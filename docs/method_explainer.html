Open-ended aggregation · internal explainer

Reading how an agent answered, not just which agent answered

Every reliability-weighting scheme we can write down is capped at +0.25 F1 on QAMPARI, and we can prove the cap. Conditioning instead on the structure of each agent's own output — where it placed a claim in its own list, and what it stayed silent about — clears that cap and beats counting in 210 of 210 agent ensembles.

2The task, precisely

A QAMPARI question — "which manga did Ryoichi Ikegami illustrate?" — has many correct answers (5 to 40, mean 10.2). Each of 8 agents returns an ordered list of entity names.

Pool every distinct normalised string across all agents. That is the candidate set — about 143 claims per question. Our job is to choose a subset of it. We are scored by set F1 against gold.

candidate claim c → who asserted it, and where in each of their lists e.g. "Crying Freeman" → grok@1, Kimi@3, MAI@7 (5 agents silent) "Sanctuary" → Kimi@41 (7 agents silent)

Only 3.5% of candidate claims are correct. The whole problem is separating that 3.5% from the rest.

3Three classes of rule

This is the single most useful idea in the project. Every method we have tested falls into one of three classes, defined by what information it is allowed to read. The classes explain all the results.

Class A

Reads the count only

How many agents asserted the claim. Nothing about which ones. This is multi-agent count and Atomic Self-Consistency.

Class B

Reads who asserted

The identities of the asserting agents — the support pattern. Every reliability-weighting scheme lives here, including correlation- and omission-aware ones.

Class C · ours

Reads the agents' output structure

Where the claim sat in each asserter's own list, how much each silent agent said, and how many claims to keep on this question.

The support pattern is the object that separates A from B. For a claim, it is which agents asserted it, not merely how many:

support count = 3 ← Class A sees this support pattern = {grok, Kimi, MAI} ← Class B sees this

With 8 agents there are 28−1 = 255 patterns but only 8 counts. The distinction matters: on QAMPARI, two-agent patterns range from 1.9% correct (MAI + gpt-5.4-nano) to 22.5% (MAI + grok) — a 12× spread at identical support count. So counting genuinely discards information.

5Why support-pattern lookup is a ceiling

This is the argument the paper turns on, and it is short.

Every reliability-weighting rule is a function of the support pattern. A weighted sum, a Naive Bayes score, a correlation penalty — each takes "which agents asserted this claim" as input and returns a number.

The support-pattern lookup arm skips the function. It looks up P(correct | exactly this subset asserted) directly from training data. So it already knows everything any such rule could know, and none of them can beat it.

The part people miss

This includes omission-aware rules. Knowing exactly who asserted a claim also tells you exactly who stayed silent — the pattern determines both. So Naive Bayes with silence cannot escape it either.

Measured, support-pattern lookup is +0.25, not significant. That is not "our weighting scheme was bad." It is: no weighting scheme can do better than +0.25 here. Which is why the only way up was to leave Class B entirely.

The reason the ceiling is so low

Counting is already an excellent filter on QAMPARI, because a solo claim is almost never right:

agents asserting12345678
share of claims87.1%6.2%3.1%1.5%0.9%0.6%0.4%0.2%
P(correct)1.2%11.1%17.4%27.2%36.5%46.3%51.9%56.5%

A solo claim is 16× less likely to be right than a supported one. Discard all solos and you have captured nearly everything the support pattern has to offer. There is almost nothing left for weighting to decide.

6Our method, step by step

Two changes to counting: one to how you score a claim, one to how many you keep.

Step 1 — score each claim

An L2-regularised logistic regression predicting P(claim correct) from four feature groups:

support pattern which agents asserted, and how many ← what counting/weighting use rank position of the claim inside each asserter's OWN list rank buckets per-agent, log-spaced — lets each agent have its own rank profile omission strength for each SILENT agent, log(how many items it listed) stacked the `pattern` probability, fed in as one more feature

Why rank works

Precision falls monotonically with position in the agent's own list:

position in list1235911162126
P(correct)29.2%31.4%30.4%26.6%17.3%15.8%11.8%8.9%6.3%

Agents put their confident answers first and pad the tail. None of this is visible in the support pattern, so it is outside the ceiling.

Why omission strength works

Every prior rule treats silence as one thing. But our agents differ enormously in how much they say — median list lengths run from 1 (gpt-5.4-nano) to 13 (Kimi), with maxima of 1,067 and 2,431 respectively.

The intuition

An agent that listed 3 items and didn't mention X has barely spoken. An agent that listed 50 items and didn't mention X has said a great deal. Weighting each silent agent's evidence by how much it actually said was the largest single feature win, +1.65.

Step 2 — choose how many to keep, per question

Sort the question's candidates by predicted probability and keep the top k:

k*(q) = argmaxk 2 · (Σi≤k pi) / (k + Ĝq) plug-in expected F1: Σp estimates hits, k is what you kept, Ĝ estimates how many gold answers exist for this question

Gold counts vary 5–40 per question, so the optimal cut is genuinely question-dependent and no single global threshold can express it.

How Ĝ is estimated — and why it barely matters

Ĝ is a ridge regression fitted on training questions only, using features available at inference: number of candidates, max support count, how many candidates have ≥2 supporters, Σ of predicted probabilities.

Not "we estimate k accurately" — we don't. It is: the keep-count must be question-dependent, and even a noisy estimate of how it should vary captures most of the value.

The crossover, resolved

Reliability weighting decays with ensemble size and goes negative by n=6 — that is the crossover we reported in August. Our method does not: it holds a significant margin at every size. The crossover is a property of Class B rules, not of aggregation. Counting itself improves with n (22.15 → 27.74) because more agents sharpen the support count; what shrinks is the headroom left for weighting.

8Are we overfitting?

Sneheel's concern, and the right one to raise. Two answers — the protocol answer, and a harder test.

The protocol answer

Everything is cross-fitted by question, 5-fold. The pattern lookup, the logistic coefficients, the gradient-boosted model, the gold-count regression and the keep threshold are all fitted on training folds and scored on a held-out fold. Nothing is tuned on what it is scored on.

This matters concretely: this project has already had a headline flip sign from +0.08 to −1.25 once thresholds were cross-fitted honestly. Anything tuned in-sample is not a result.

The harder test — leave-one-source-out

Random folds draw train and test from the same question distribution. So a rule exploiting something peculiar to QAMPARI-as-a-whole would still look fine. QAMPARI ships five structurally different question sources; we train on four and test on the fifth.

80–90% of the gain survives a complete change of question type. Two things worth noticing beyond that headline:

The test has teeth

support-pattern lookup is a 28-cell lookup table — literally the memorisation the concern describes. Under random folds it is +0.25; under distribution shift it collapses to +0.02, ns. So the protocol does detect pattern-memorisation, and our features are not what it flags.

Consequence for the paper

The gradient-boosted model transfers worst. Out of distribution rank scorer + budget (31.48) now beats rank scorer + boosting + budget (31.44). The extra capacity buys +0.3 in-distribution and costs more than that out of it. Make rank scorer + budget the headline method — plain logistic plus the budget. Simpler to describe, one fewer moving part, more robust.

9Predicting the gain

Requested at the 21 Aug meeting: given a pool of models, can we predict how much our method will help? Yes — leave-one-out R² = 0.817.

Regressing the gain over the best single agent on properties computable before running the method, across all 210 ensembles:

dominance — best ÷ mean of the rest−0.620+0.687
solo ratio−0.595+0.328

Why our two results tables look so different

Dominance flips sign between them. One dominant model makes counting bad — so we beat counting easily (+0.687) — while simultaneously making the best single agent hard to beat (−0.620). Table 1 and Table 2 are not two views of one thing; they are driven by the same variable in opposite directions.

Parsimonious version for the paper — three interpretable quantities, size + dominance + (union recall − best agent's recall), gives leave-one-out R² = 0.642. Dominance alone gives 0.368.

Why the transfer is uneven — the solo ratio

Once you keep everything with ≥2 supporters, the only decision weighting changes is whether to admit a solo claim. So its value is set entirely by how informative a solo claim is. Define:

solo ratio = P(correct | exactly 1 agent asserts) ÷ P(correct | ≥2 agents assert)

Why list length was dropped, in detail

It is a fair question, because the raw signal looks strong: precision falls from 30.2% for items from a short list to 3.4% for items from a long one, a 26.7-point spread. Three things explain why it contributes +0.01 anyway.

Precision by list lengthshort (<10)medium (10–24)long (25+)spread
ignoring position30.2%22.8%3.4%26.7 pts
within positions 1–330.5%33.3%24.1%9.2 pts
within positions 4–1029.7%23.5%15.4%14.3 pts
within positions 11+—15.3%2.2%13.1 pts
 Controlling for position removes half to two-thirds of the apparent length effect.
  1. Most of it is position in disguise. An item at position 40 can only exist in a list of at least 41 items, so long lists are largely lists with many high-position items. Conditioning on position removes half to two-thirds of the spread.
  2. The remainder is already captured by relative position (position ÷ list length), which is part of the position feature block. "Item 11 of 12" and "item 11 of 500" are already distinguished.
  3. What is left sits where the decision is already made. 98,000 of roughly 141,000 assertions are position-11-or-later inside long lists, at 2.2% precision — 70% of the mass, already excluded by position alone. It barely touches the marginal keep-or-drop calls.
Why the same quantity earns its place on the omission side

A silent agent has no position. There is no rank to condition on, so how much it said is the only thing you know about it. That is why list length is redundant for agents that asserted (+0.01) and irreplaceable for agents that stayed quiet (+0.33) — and why omission strength is in the method while verbosity is not.

Prior art we must cite, not claim

Dawid–Skene. Our Naive Bayes with silence and support-pattern lookup arms are, in substance, a classical annotator -reliability model applied to LLM agents. Cite the crowdsourcing literature and present them as baselines and ceilings, not contributions. This strengthens the argument: even the classical ceiling is +0.25 ns, and output-structure signals beat it.

One useful confirmation

The Optimal Weight paper we extend (arXiv:2510.01499) targets binary/categorical predictions, not set-valued generation. Its log(p / (1−p)) weight requires per-model accuracy > 0.5; our per-claim precisions run 5.8–28%, so every weight goes negative and the method inverts. That is the cleanest possible statement of the gap we fill.

12Open items

  • ASQA per-ensemble table is incomplete — it has counting vs weighting only; our method is not in it. ~30–45 min, free.
  • Paper-exact single-model ASC needs new generation (777 × m calls on one model). The current ASC arm substitutes agents for stochastic samples — unavoidable from cache, and it is the extension we propose, but it should be stated.
